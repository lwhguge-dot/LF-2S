# 预览稳定性排查与 0.3.1 修复

2026-10-16 用户反馈连接后很快失效。用户日志在 21:09:03 与 21:10:09 记录 `/preview` 的 ConnectionAbortedError；Windows WLAN 事件显示该时段持续连接 ESP32，21:10:31 才切回普通 Wi-Fi。不能将应用请求失败直接归因为热点物理断线。

同一板卡/固件 0.1.4 上复现 0.3.0：约 9.735 秒、5 张 JPEG 后进入 error，最后请求约 2313 ms。此前成功传输多次为 1.3–1.9 秒。失败后仍连接同一热点，直接读取 `/health` 正常；没有据此认定板卡损坏或重启。

应用存在两项缺陷：普通 HTTP 统一在 2 秒强制 shutdown，包括传输较大的 SVGA JPEG；任何网络读取异常立即变为永久 error，后台不再核对。esp32-camera 一次帧等待本身最多约 4 秒，故 2 秒显示请求预算不能覆盖全部有效响应。0.3.0 的十余张图像短测没有覆盖这种情况。

0.3.1 的预览传输允许 6 秒、状态 2 秒、对焦 5 秒，连接 1 秒；保留独立绝对截止和有界响应，不因放宽期限宣称图像新鲜度合格。IPC 等待 12 秒覆盖串行健康核对和预览。画面仍在 2 秒显示期限后隐藏，慢传输期间不把旧图当作实时图。

临时传输失败、超时、不完整响应或 503/504 清除健康状态和画面，进入 recovering。后台按 0.75 秒乘连续次数的退避重新 GET 状态，最多连续三次失败；仅原先配对的 camera_stream_id、协议和未标定台架配置一致时才恢复。不能以 health 缓存已清空为由接纳新流。流变化、身份/模式错误、畸形头、JPEG/编号校验错误仍立即阻断并需手动重连。没有自动重发对焦、飞行或协议动作。

实物日志标记 simulation=false；按 response_timeout/connection_interrupted/incomplete_response 等记录端点、耗时与 Windows 错误。页面显示传输异常/恢复计数，通用“请求失败”不再掩盖所有原因。持续无响应仍需确认电脑是否连接 ESP32 热点；该热点没有互联网，切回普通 Wi-Fi 后无法读取 192.168.4.1。

软件回归见 `tests/test_esp32.py`：大于 2 秒的完整有效 JPEG、短暂异常与对焦不重发、三次失败上限、恢复期间相机重启拒绝，以及原有有界读取/迟到响应/回放隔离。实板基线与修复连续测试原始文件保存在研发目录 `P1/03_esp32_idf/evidence/hardware/20261016-preview-stability`，可公开摘要单独保存；不把短时运行解释为长期射频、供电或飞行验收。
